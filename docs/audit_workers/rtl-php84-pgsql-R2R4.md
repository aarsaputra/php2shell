# Sweep Gap-Rule R2 (raw-ptr-cache) + R4 (pre-init-exec) — ext/pgsql, PHP 8.4.27

Auditor sweep per-pohon. Sumber: `/run/media/lota1337/AarSSDaputra/p2s-lab/asanbuild/php-8.4.27` (baik 8.4.26 maupun 8.4.27 tersedia, dibaca read-only, tanpa build/eksekusi).
Metode: diff tag `php-8.4.26...php-8.4.27` via GitHub compare API (lengkap 166 commit, 300 file — **ext/pgsql: 0 file berubah**; patch reference disimpan di `/tmp/diffsrc/`) → karena tidak ada silent-fix segmentation, sweep manual menyeluruh dilakukan terhadap seluruh `pgsql.c` (6394 baris) + `php_pgsql.h` untuk pola R2 (pointer mentah yang hidup lebih lama dari pemiliknya) dan R4 (eksekusi sebelum init selesai). Setiap kandidat diuji dengan 5 filter kognitif. Static reading = kandidat, bukan temuan; tidak ada build ASAN/eksekusi PoC (sumber read-only per batasan tugas).

## Kandidat lolos filter (untuk verifikasi ASAN/dinamis lanjutan)

### K-1 — `pgsql_result_handle.conn` / `pgLofp.conn`: PGconn* mentah di objek PHP yang bisa hidup lebih lama dari pemilik link (UAF use `PQexec`/`lo_read` pada PGconn yang sudah di-close)
- **Bentuk:** kelima situs result-object dibuat (`pgsql.c:1206` pg_query, `:1333` pg_query_params, `:1419` pg_execute, `:1534` pg_prepare+pg_execute jalur async, `:4289` pg_get_result, `:5793` wrapper async) semuanya hanya menyalin pointer `pgsql` ke `pg_result->conn` tanpa `GC_ADDREF(link_obj)` / tanggungan refcount ke object link:
  ```c
  object_init_ex(return_value, pgsql_result_ce);
  pgsql_result_handle *pg_result = Z_PGSQL_RESULT_P(return_value);
  pg_result->conn = pgsql;   // ← borrow mentah, tidak rooted
  pg_result->result = pgsql_result;
  ```
  Sama untuk `pgsql_lofp->conn = pgsql` (`pgsql.c:2717`, pg_lo_open).
- **Jalur bebas pemilik:** `pg_close($conn)` (`pgsql.c:885-913`) — `CHECK_PGSQL_LINK(link)` hanya dipanggil sebelum close, lalu `pgsql_link_free(link)` (baris 176-199) langsung `PQfinish(link->conn)` untuk non-persistent + `link->conn = NULL`. `unset($conn)` yang membuat refcount link habis → `pgsql_link_free_obj` → `pgsql_link_free` → `PQfinish` dengan efek sama. Setelah itu:
  - `pg_field_table($res, …)` (`pgsql.c:1721-1747`) tetap memakai `pg_result->conn` untuk `PQexec(pg_result->conn, "select relname from pg_class …")` — guard `CHECK_PGSQL_RESULT(pg_result)` (didefinisikan `pgsql.c:101-104`) **hanya** mengecek `result != NULL`, bukan `conn != NULL` / validitas PGconn.
  - `pg_field_name`/`pg_field_type` (via `php_pgsql_get_field_info` `pgsql.c:1812` → `get_field_name(pg_result->conn, …)`, `get_field_name` `pgsql.c:1656-1691` mengeksekusi `PQexec(pgsql, "select oid,typname from pg_type")`) — guard sama-sama hanya `CHECK_PGSQL_RESULT`.
  - Semua `pg_lo_*` (`pg_lo_read` `:2772`, `pg_lo_write` `:2819`, `pg_lo_read_all` `:2844`, `pg_lo_seek` `:3016-3018`, `pg_lo_tell` `:3045-3050`, `pg_lo_truncate` `:3074-3079`) memakai `pgsql->conn` via `CHECK_PGSQL_LOB` (`:105-108`) yang **hanya** mengecek `lob->conn == NULL` — tapi `lob->conn` TIDAK di-nol-kan saat link di-close (hanya di-nol-kan pada link handle sendiri), sehingga guard ini tidak melindungi sama sekali terhadap PGconn yang sudah di-`PQfinish` (pointer dangling, bukan NULL).
- **Konsekuensi:** setelah `PQfinish`, blok PGconn dialokasikan-ulang; use kembali (`PQexec`, `lo_read`, …) = use-after-free klasik pada heap libpq (bukan heap Zend). Dampak menurut ASAN: heap-use-after-free read/write. Eksploitability umum: libpq umumnya crash/UB, bukan primitif yang mudah dikendalikan — tapi pola mem-unsafety-nya nyata dan triggerable murni dari PHP script biasa.
- **Filter:**
  1. COW/aliasing? Tidak berlaku — pointer libpq heap, bukan zend_string/array; tidak ada COW safety net.
  2. Akses per-nama / per-iterasi? Tidak relevan — trigger adalah urutan statement (close lalu pakai).
  3. User code bisa jalan di tengah frame? Tidak diperlukan — UAF antar-frame PHP, bukan di tengah satu frame C.
  4. Guard eksisting? **Tidak memadai**: `CHECK_PGSQL_RESULT`/`CHECK_PGSQL_LOB` mengecek field yang salah (`result`/field yang tidak di-nol-kan saat PQfinish); tidak ada doubly-linked lifetime antara Result/Lob object dan Connection object.
  5. Global atau milik objek? Milik objek (`pgsql_result_handle.conn`, `pgLofp.conn`), non-rooted — persis definisi R2 raw-ptr-lives-longer-than-owner.
- **Mengapa tidak tertambal di 8.4.27 / master:** cek master `php-src` `ext/pgsql/php_pgsql.h` @ master (fetch 2026-10-25): `pgsql_result_handle` masih persis sama (`PGconn *conn; PGresult *result; int row;` tanpa `zend_object *link`), dan situs `pg_result->conn = pgsql;` di master `pgsql.c:1190` dst. identik — PHP belum menganggap ini perlu diperbaiki hingga master.
- **Status literatur:** telusur issue tracker php-src via GitHub search API (2026-10-25) menemukan satu issue terkait: GH-19484 "pgsql: potential use after free when using persistent connections" (closed 2025-08-15, fix masuk jauh sebelum 8.4.26) — tapi itu jalur **notice-handler persistent** (sudah di-cover gugur bare #1, sesuai fix resmi yang men-set no-op processor saat rollback), **bukan** jalur `result.conn`-after-close yang dilaporkan di K-1. Tidak ada issue untuk `pg_field_table`/`pg_lo_*`/`pg_fetch_*` setelah `pg_close`/unset pada koneksi non-persistent. Secure-by-contract tidak: perilaku "Result valid setelah conn ditutup" tidak didokumentasikan sebagai legal, tapi juga tidak dilarang eksplisit dengan exception — statusnya grey zone API kontrak.
- **Verdict: (a) unknown-unknown (kandidat kuat).** Sebelum naik ke laporan, wajib reproduksi ASAN: script PHP 20-baris (`pg_connect` → `pg_query` → `pg_close` → `pg_field_table`/`pg_lo_read`) pada build `--enable-embedded-pgsql`/libpq ASAN (atau build PHP ASAN biasa + libpq sistem — UAF libpq akan tetap ditangkap ASAN sebagai free-freed heap use jika libpq ikut di-compile dengan ASAN, atau minimal dapat diverifikasi dengan trip `PQstatus` garbage read). Ini bukan silent-fix dan bukan known-bug — ni sebuah kandidat klasik R2 yang lolos semua audit lama.

### Bersih dengan bukti — pola R2/R4 yang diuji dan gugur dengan alasan line-numbered

1. **Notice handler `_php_pgsql_notice_handler(void *l, …)`** (`pgsql.c:321-346`): pointer mentah `pgsql_link_handle*` dipasang ke libpq via `PQsetNoticeProcessor` (dipasang `pgsql.c:832-835` set link dibuat). Kandidat R2 klasik (callback libpq bisa menyala kapan saja asal ada traffic — termasuk saat link object sudah half-destroyed? — dan menyentuh `link->notices`).
   **Gugur:** (i) handler pertama-gama cek `l == NULL` return (`:323-325`), (ii) `pgsql_link_free` tidak pernah dipanggil selama link masih memiliki notice processor aktif dengan `link` valid — `PQfinish` dipanggil *di dalam* `pgsql_link_free` setelah pointer link tidak akan pernah dilihat libpq lagi (`PQsetNoticeProcessor` hanya bisa menyala dari panggilan libpq lain on the same PGconn, dan setelah `PQfinish` PGconn itu sendiri sudah mati), (iii) di jalur RSHUTDOWN persistent `_rollback_transactions` (`pgsql.c:356-365`) notice processor **di-unset dulu** (`PQsetNoticeProcessor(link, NULL, NULL)` + re-set hanya jika terdeteksi) sebelum operasi rollback — jadi tidak ada jendela di mana handler mengejar link yang sudah setengah lepas.
2. **Cache `PGG(field_oids)` / `PGG(table_oids)`** (` HashTable` global, di-init RINIT `pgsql.c:629-630`, di-destroy RSHUTDOWN `:641-642`): kandidat R3/R2 (zend_string mentah di global melewati batas request). **Gugur**: lifecycle request-bounded via `zend_hash_init`/`zend_hash_destroy` berpasangan dengan `release_string` dtor (`pgsql.c:629-630, 641-642`); nilai yang di-cache (`zend_string_init` di `:1686`, `:1758`) di-copy sebelum `PQclear(result)` (`:1689` `ret = zend_string_copy(name)` — string hidup setelah PGresult dibebaskan), value keluar via `RETURN_STR_COPY` (`:1737`, `:1760-1761`) — tidak ada raw pointer yang menggantung melampaui umur HT.
3. **`PGG(connections)`** (`HashTable` global hash dari link objects, update `pgsql.c:823`, del di free `:188`): kandidat R2 (hash global menyimpan zval object). **Gugur**: entri disimpan sebagai zval object dengan refcount yang di-hold oleh hash (via `zend_hash_update(&PGG(connections), str.s, return_value)` — return_value refcounted) — bukan pointer mentah; del selalu berpasangan dengan release link lifetime (`pgsql.c:188` dijalankan di free handler → hash entry dihapus tepat saat object mati, tidak ada dangling entry).
4. **`PGG(default_link)`** (`zend_object*` global): kandidat R2/R3. **Gugur**: `php_pgsql_set_default_link` (pgsql.c:296-305) `GC_ADDREF(obj)` sebelum menimpan dan `zend_object_release` saat menimpa / di RSHUTDOWN (`:636-639`); RINIT me-reset ke NULL (`:627`) — rooted dengan benar, tidak ada dangling antara request (FSM idle-no-op seperti di ext/intl RINIT tapi dengan tambahan reset eksplisit global yang memang menyimpan object).
5. **`PGG(regexes[PGSQL_MAX_REGEXES])`** (`pgsql.c:510` init persistent `zend_string_init(…, true)` di GINIT-equivalent (di MINIT-ini section `:493-510` makro STD_PHP_INI + register), di-release di MSHUTDOWN `:619-621`): kandidat R2 request-boundary. **Gugur**: string di-alokasi `persistent=true`, dihancurkan `zend_string_release_ex(…, true)` di MSHUTDOWN — lifecycle process-scoped persis seperti alokasinya; RSHUTDOWN tidak menyentuhnya (benar, bukan bug). Tidak ada pointer request-bound yang menggantung.
6. **`pgsql_result_handle.conn` di situs yang bisa dianggap "safe"**: `pg_get_result` (`:4289`) dan wrapper async `:5793` — keduanya memakai link yang `CHECK_PGSQL_LINK`-guarded pada frame aktif yang sama, jadi di saat pointer disalin link pasti masih hidup; yang rawan adalah penggunaan *berikutnya* di frame PHP berbeda — sudah di-cover K-1 (bukan gugur, hanya tidak menambah kandidat baru di luar K-1).
7. **R4 pre-init-exec — comprehensive sweep**: semua entry point result/lob/link fetch (`CHECK_PGSQL_LINK` `:92-96`, `CHECK_PGSQL_RESULT` `:101-104`, `CHECK_PGSQL_LOB` `:105-108`) mengecek kekosongan sebelum dereference — untuk *field yang sesuai*; kasus conn-check yang kurang tepat sudah di-cover K-1 (bukan R4 — bukan kode berjalan sebelum init, melainkan use-after-lifetime). Tidak ada jalur di pgsql yang bisa mengeksekusi query terhadap state yang belum selesai init (semua `pg_connect` path selesai `PQconnectdb*` + set notice processor sebelum object dikembalikan `pgsql.c:766-835`; persistent reuse path `:780` set default link setelah link valid).
8. **`_php_pgsql_trim_message` / `PHP_PQ_ERROR`** (`pgsql.c:285-294`): pointer `char*` dari `PQerrorMessage(pgsql)` di-trim via `zend_string_init` (copy) langsung lalu di-set-released — tidak ada penyimpanan pointer mentah libpq melebihi panggilan berikutnya. Gugur.
9. **`pg_lo_import`/`pg_lo_unlink`/`pg_lo_open` chain** (`pgsql.c:2700-2730`): `pgsql_lofp->conn = pgsql` hanya dipasang setelah `lo_open` sukses — tidak ada pre-init-exec. Untuk lifetime: sama dengan K-1 (borrowed conn) — sudah tercakup K-1, tidak kandidat baru.
